# 0006. REST API 공통 규칙

- 상태: 제안
- 날짜: 2026-10-28

## 맥락

모든 모듈이 같은 규칙으로 응답해야 클라이언트(홈페이지, 관리자 화면, 보호자 화면)가 단순해진다.
규칙을 모듈마다 따로 정하면 에러 형식, 페이지네이션, 동시 수정 처리가 제각각이 된다.

## 결정

**경로와 버전**
- `/api/v1/...` 형태로 버전을 경로에 둔다.
- 리소스는 복수형 명사, 하위 리소스는 계층으로 표현한다. 예: `/api/v1/inquiries/{id}/consultations`
- 상태 변경처럼 CRUD로 표현하기 어려운 동작은 하위 리소스로 표현한다. 예: `POST /api/v1/applications/{id}/approvals`

**상태 코드**
- 생성: `201 Created` + `Location` 헤더
- 오래 걸리는 작업: `202 Accepted` + 작업 상태 조회 경로
- 내용 없는 성공: `204 No Content`
- 인증 실패 `401`, 권한 없음 `403`, 다른 기관 리소스 `404` (0004)
- 상태 충돌 `409`, 동시 수정 충돌 `412`, 검증 실패 `422`, 요청 과다 `429`

**에러 형식**
- RFC 9457 Problem Details (`application/problem+json`). Spring의 `ProblemDetail`을 사용한다.
- 필드 검증 오류는 `errors` 확장 필드에 필드명과 메시지 목록으로 담는다.
- 에러 메시지에 개인정보를 넣지 않는다.

**동시 수정과 중복 요청**
- 수정 가능한 리소스는 `ETag`를 내려주고, 수정 요청은 `If-Match`를 요구한다. 버전이 다르면 `412`.
- 신청 제출처럼 중복되면 안 되는 `POST`는 `Idempotency-Key` 헤더를 받는다. 같은 키로 다시 오면 처음 결과를 그대로 돌려준다.

**조회**
- 목록은 커서 기반 페이지네이션 (`cursor`, `size`). 응답에 다음 커서를 포함한다.
- 필터는 쿼리 파라미터로, 정렬은 `sort=field,asc` 형식으로 한다.

**시간과 형식**
- 시간은 ISO 8601, 오프셋 포함 (예: `2026-12-01T09:00:00+09:00`)
- JSON 필드명은 camelCase

**문서**
- Spring REST Docs로 테스트를 통과한 API만 문서에 나오게 한다. 문서와 실제 동작이 어긋나지 않게 하기 위해서다.

## 결과

- 얻는 것: 모든 모듈이 같은 방식으로 실패하고 같은 방식으로 페이지를 넘긴다. 동시 수정과 중복 제출을 HTTP 수준에서 막는다.
- 감수하는 것: `ETag`와 `Idempotency-Key` 처리를 공통 컴포넌트로 먼저 만들어야 한다.
