# 0003. 인증: 사용자 유형별 인증 방식 분리

- 상태: 제안
- 날짜: 2026-10-28

## 맥락

이 서비스를 쓰는 사람은 세 부류이고, 기기 환경과 사용 빈도가 다르다.

| 사용자 | 특징 |
|---|---|
| 직원 (기관 관리자, 종사자) | 매일 사용, PC와 휴대폰 모두 사용 |
| 보호자 | 가끔 사용, 연령대 다양, 비밀번호를 기억하기 어려울 수 있음 |
| 문의자 | 한두 번 사용, 회원가입을 기대하기 어려움 |

한 가지 방식으로 모두를 처리하면 보호자와 문의자에게 너무 어렵거나, 직원에게 너무 약하다.

## 선택지

- 세션 기반 인증: 서버가 상태를 관리, 즉시 로그아웃 쉬움. 모바일·외부 클라이언트 확장에 불리
- JWT만 사용: 서버가 상태를 거의 안 가짐. 탈취 시 만료 전까지 막기 어려움
- JWT access + DB 저장 refresh 토큰: 짧은 access로 피해 범위를 줄이고, refresh는 서버가 통제

## 결정

**직원**
- 아이디·비밀번호 로그인. 비밀번호는 일방향 해시(BCrypt 이상)로 저장
- access 토큰(JWT, 짧은 수명) + refresh 토큰(긴 수명)
- refresh 토큰은 해시로 DB에 저장하고 사용할 때마다 새 토큰으로 교체(rotation)
- 이미 사용된 refresh 토큰이 다시 들어오면 탈취로 보고 그 사용자의 토큰 묶음 전체를 폐기
- 로그인 실패가 반복되면 일시 잠금

**보호자**
- 기관이 발급하는 초대 링크로 가입 (일회용, 만료 시간 있음, 특정 이용자와 연결됨)
- 로그인은 휴대폰 번호 + 일회용 인증번호(OTP)를 기본으로 검토. 문자 발송 비용과 공급자는 별도 결정
- 이후 토큰 체계는 직원과 같음

**문의자 (비회원)**
- 회원가입 없이 문의 등록
- 진행 상황 확인이 필요하면 문의 시 받은 연락처로 일회용 인증 후 짧은 수명 토큰 발급
- 이 토큰은 해당 문의 한 건만 볼 수 있음

**공통**
- 토큰은 HTTPS로만 전달
- 주민등록번호는 인증에 쓰지 않음 (개인정보 보호법상 처리 제한)

## 결과

- 얻는 것: 사용자별로 부담은 낮추고 위험은 통제한다. refresh 토큰 재사용 감지로 탈취에 대응한다.
- 감수하는 것: 인증 경로가 세 가지라 구현과 테스트가 늘어난다. 문자 인증은 비용이 생긴다.

## 다시 볼 조건

- 보호자 인터뷰에서 휴대폰 인증이 어렵다는 피드백이 나올 때 (카카오 로그인 등 대안 검토)
- 기관이 기존 계정 체계(예: 사내 SSO)를 요구할 때
