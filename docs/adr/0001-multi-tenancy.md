# 0001. 멀티테넌트: 공유 스키마 + 기관 ID

- 상태: 확정 (2026-10-28, TASK-002에서 구현·검증)
- 날짜: 2026-10-28

## 맥락

첫 사용 기관은 한 곳이지만, 같은 지역에도 주간활동·방과후활동 제공기관이 여러 곳 있다.
처음부터 여러 기관이 같은 서비스를 쓰는 구조로 만들어야 나중에 다시 설계하지 않는다.
기관 사이의 데이터는 절대 섞이면 안 된다. 장애·건강 정보를 다루기 때문에 한 번의 누락이 곧 개인정보 유출이다.

## 선택지

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 기관별 DB | 격리가 가장 강함 | 기관마다 DB 비용과 마이그레이션 부담. 소규모 기관 다수에는 과함 |
| B. 기관별 스키마 | 격리가 강함, DB는 하나 | 스키마 수만큼 마이그레이션 반복, 커넥션 관리 복잡 |
| C. 공유 스키마 + 기관 ID 컬럼 | 운영이 단순, 기관 추가가 행 하나 추가로 끝남 | 쿼리에서 기관 조건을 빠뜨리면 데이터가 섞임 |

## 결정

**C. 공유 스키마 + 기관 ID(`org_id`) 컬럼**을 쓴다. 대신 "조건 누락" 위험을 여러 겹으로 막는다.

1. 애플리케이션: 기관 소유 엔티티는 모두 `org_id`를 가지며, Hibernate의 테넌트 식별자 기능(`@TenantId`)으로 조회와 저장에 기관 조건이 자동으로 붙게 한다.
2. 요청 경계: 인증된 사용자의 소속 기관을 요청마다 테넌트 컨텍스트에 넣고, 요청이 끝나면 반드시 비운다.
3. DB: PostgreSQL 행 수준 보안(RLS)을 2차 방어선으로 켠다. 애플리케이션 버그로 조건이 빠져도 DB가 다른 기관 행을 돌려주지 않는다.
4. 테스트: "기관 A 사용자로 기관 B 데이터 조회 시 실패"를 모든 조회 API의 공통 테스트로 둔다.

## 결과

- 얻는 것: 기관 추가가 쉽고, 운영할 DB가 하나다. 격리는 애플리케이션과 DB 두 겹으로 보장한다.
- 감수하는 것: 모든 테이블에 `org_id`와 인덱스가 필요하다. RLS 설정과 커넥션별 세션 변수 관리가 추가된다.
- 주의: 기관 간 공통 데이터(코드표 등)는 `org_id` 없는 별도 테이블로 분리한다.

## 다시 볼 조건

- 특정 기관이 물리적으로 분리된 저장소를 요구할 때
- 기관 수가 수백 곳을 넘어 한 DB의 부하가 문제가 될 때
