# 0005. 민감정보 보호: 애플리케이션 레벨 암호화와 접속기록

- 상태: 제안
- 날짜: 2026-10-28

## 맥락

이 서비스는 장애 유형, 알레르기 같은 건강 정보를 다룬다. 개인정보 보호법상 민감정보다.
관련 기준(개인정보의 안전성 확보조치 기준, 2026-07-01 시행)에서 확인한 요구사항은 다음과 같다.

- 비밀번호는 일방향 암호화
- 주민등록번호, 계좌번호 등은 암호화해서 저장
- 민감정보나 고유식별정보를 처리하는 시스템은 접속기록을 2년 이상 보관
- 민감정보는 다른 개인정보와 별도로 동의를 받아야 함
- 보유기간이 끝나면 복원할 수 없게 파기

## 선택지

| 방식 | 장점 | 단점 |
|---|---|---|
| 디스크 전체 암호화만 | 설정만으로 끝남 | DB에 접속한 사람에게는 평문으로 보임 |
| DB 함수 암호화 (pgcrypto) | 쿼리에서 바로 처리 | 키가 SQL과 로그에 노출될 위험 |
| 애플리케이션 레벨 암호화 | 키가 DB에 가지 않음, DB가 유출돼도 암호문 | 암호화된 컬럼은 검색·정렬이 어려움 |

## 결정

**수집 최소화가 먼저**
- 주민등록번호는 수집하지 않는다. 필요한 업무는 공공 시스템(전자바우처 등)에 맡긴다.
- 기능에 꼭 필요한 민감정보만 받고, 항목마다 수집 목적을 문서로 남긴다.

**암호화**
- 민감정보 컬럼은 애플리케이션에서 AES-GCM으로 암호화해 저장한다 (JPA `AttributeConverter`).
- 암호문 앞에 키 버전을 붙여 키 교체(rotation)를 할 수 있게 한다.
- 키는 저장소와 DB에 두지 않고 환경 변수나 비밀값 관리 서비스로 주입한다.
- 정확히 일치하는 검색이 필요한 값(예: 휴대폰 번호)은 별도의 HMAC 값을 같이 저장해 검색한다.

**동의**
- 일반 개인정보 동의와 민감정보 동의를 따로 받고, 동의 시점·항목·버전을 기록한다.
- 사진 촬영·공개 동의도 같은 구조로 관리한다.

**접속기록**
- 개인정보를 조회·수정·다운로드한 기록(누가, 언제, 무엇을, 어디서)을 추가만 가능한 테이블에 남긴다.
- 보관기간은 2년 이상.

**파기**
- 데이터마다 보유기간을 두고, 만료된 데이터는 배치로 파기한 뒤 파기 기록을 남긴다.

## 결과

- 얻는 것: DB나 백업이 유출돼도 민감정보는 암호문이다. 법적 요구사항을 설계 단계에서 반영한다.
- 감수하는 것: 암호화 컬럼은 부분 검색과 정렬을 할 수 없다. 키 관리와 교체 절차가 필요하다.

## 다시 볼 조건

- 기관이 암호화된 항목으로 검색·통계를 꼭 해야 할 때
- 관련 고시나 지침이 바뀔 때
